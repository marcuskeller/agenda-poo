02 / PONTO DE PARTIDA Agenda estruturada

Primeiro, a versão procedural.

Estrutura simplificada

estruturada/
├── config/
│   ├── database.php
│   └── agenda.sql
├── index.php
├── create.php
├── edit.php / update.php
└── delete.php / error.php

Como funciona

Uma operação por arquivo

Os arquivos executam o fluxo diretamente. Em create.php, o formulário, a validação e a inserção no banco convivem no mesmo lugar.

A conexão já fica separada em config/database.php.

É simples para começar, mas a mistura de responsabilidades pode dificultar a evolução do CRUD.

03 / NOVA ESTRUTURA Agenda orientada a objetos

Depois, a versão POO.

Estrutura simplificada

app/
├── Controller/     requisições e ações
├── Models/         entidades, serviços
│                   e repositórios
├── Views/          telas
└── Infrastructure/ conexão e sessão

Ideia central

Cada parte tem um papel mais claro e trabalha junto com as outras.

Contatos, usuários e autenticação são organizados em componentes com responsabilidades distintas.

04 / RESPONSABILIDADES Do formulário ao banco

Como nasce um contato?

01 / Controller

Recebe

ContactController lê os dados e chama o serviço.

02 / Service

Coordena

ContactService organiza o cadastro e verifica duplicidade.

03 / Entity

Representa

ContactEntity guarda os dados e valida nome, telefone e e-mail.

04 / Repository

Persiste

ContactRepository executa a inserção no banco.

A view apresenta o formulário e os retornos; o controller coordena a resposta para a tela.

05 / ANALOGIA Uma agenda no escritório

Uma pessoa ou uma equipe?

Procedural

Uma pessoa cuida de tudo

Ela recebe o contato, confere os dados e guarda a ficha. Cada tarefa segue um conjunto de instruções.

POO neste projeto

Papéis divididos

Uma pessoa recebe, outra organiza e confere, e outra guarda a ficha. Cada parte colabora para concluir o trabalho.

É uma analogia para a organização adotada aqui: tanto código procedural quanto POO podem dividir responsabilidades.

06 / FUNCIONALIDADE ADICIONAL Acesso e perfis

Uma agenda, dois perfis.

A versão POO acrescenta cadastro, login e controle de acesso por sessão.

USER / Usuário comum

Sua própria agenda

Cria, consulta, edita e exclui seus contatos. Os registros são vinculados ao usuário.

ADMIN / Administrador

Gestão de usuários

Lista e edita usuários, além de ativar ou inativar contas; não pode inativar a própria conta.

O cadastro pela tela cria um usuário comum. O perfil determina a área apresentada após o login.

07 / CONCEITOS Orientação a objetos

Dados e comportamentos juntos.

Exemplo / ContactEntity

private string $name = '';
private string $phone = '';

public function getName(): string
{
    return $this->name;
}

O que estamos vendo

  • Classe: representa um contato.
  • Atributos: guardam nome e telefone.
  • Métodos: oferecem operações, como ler o nome.
  • Encapsulamento: atributos privados são acessados por métodos.

fill() preenche os dados; a validação é uma etapa separada, chamada pelo serviço no cadastro e na edição.

08 / ARQUITETURA MVC e contratos

Separar para entender.

Model

Dados e regras

Entidades, serviços e repositórios trabalham com os dados e suas operações.

View

Apresentação

Telas exibem formulários, listas e mensagens para quem usa o sistema.

Controller

Fluxo

Recebe ações, chama serviços e direciona a resposta para a interface.

As interfaces ContactRepositoryInterface e UserRepositoryInterface definem contratos. Os serviços ainda criam repositórios concretos diretamente, portanto há espaço para reduzir o acoplamento.

09 / DIAGRAMA DE CLASSES Contatos

Como as classes colaboram.

Legenda: + público; − privado; # protegido; seta tracejada aberta = usa; triângulo tracejado = implementa interface; triângulo contínuo = herda. Membros e relações selecionados; … omite parâmetros. Em telas pequenas, role o diagrama horizontalmente. O controller também usa Auth, UserService e GlobalMessages.

10 / DIAGRAMA DE CLASSES Usuários e autenticação

Acesso e usuários em conjunto.

Legenda: + público; − privado; # protegido; seta tracejada aberta = usa; triângulo tracejado = implementa interface; triângulo contínuo = herda; {static} = método estático. Membros e relações selecionados; … omite parâmetros. Os controllers também usam GlobalMessages. Em telas pequenas, role o diagrama horizontalmente.

11 / CONCLUSÃO Escolhas de projeto

Organizar é fazer escolhas.

E a herança?

Foi aplicada aos controllers.

ContactController, AuthController e UserController herdam de BaseController, que compartilha a conexão e operações HTTP comuns.

implements cumpre um contrato de interface; extends herda comportamento de uma classe-base.

O que aprendemos

A procedural é direta. A POO facilita localizar e evoluir responsabilidades à medida que o projeto cresce.

A versão POO também amplia o escopo: autenticação e gestão de usuários não existiam no CRUD procedural analisado.
